Build on BT DataPlug

One REST API for airtime, data bundles, electricity tokens and cable TV. Test free in a sandbox, then go live from your wallet.

Get API keysInteractive reference

Overview

All requests go to {{ base_url }} over HTTPS and exchange JSON. Prices are set by BT DataPlug on the server: you only send which plan or amount you want, never a price. Live orders are paid from the wallet of the account that owns the application.

Quickstart

  1. Open the console, enable developer access and create a test application.
  2. Copy the secret key immediately (shown once). Keep it on your server, never in a mobile app or browser.
  3. Check your connection: GET /balance/.
  4. List plans: GET /data-plans/?network=MTN.
  5. Buy: POST /data/ with an Idempotency-Key.
  6. Poll GET /transactions/{reference}/ or receive a webhook.
  7. Create a live application, wait for approval, fund your wallet, and swap the keys.

Authentication

Every request carries two headers:

X-API-Key: pk_test_xxxxxxxxxxxxxxxxxxxxxxxx
Authorization: Bearer sk_test_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

Secrets are stored hashed, so we cannot show them again. If you lose one, regenerate it in the console (the old one stops working at once). Revoke an application if a secret leaks.

Always call the API from your server. Optionally restrict the application to your server's IPs in the console.

Environments

Key prefixBehaviour
pk_test_ / sk_test_Sandbox. No wallet charge and no provider call. Same URL. Orders are simulated: a recipient ending in 0000 fails, ending in 9999 stays pending, anything else succeeds. Webhooks fire normally.
pk_live_ / sk_live_Real purchases charged to your wallet. The application must be approved by BT DataPlug first.

Test and live orders are stored separately and never appear in each other's lists.

Idempotency

Every purchase must include Idempotency-Key (8 to 64 characters, unique per order, e.g. a UUID you store with your order). If your request times out or you are unsure whether it went through, retry with the same key:

  • Same key + same body: you get the original result back (idempotent_replay: true); you are never charged twice.
  • Same key + different body: 422 idempotency_key_reused.
  • Original still running: 409 request_in_progress. Wait and retry.
Never generate a new key to retry a timed-out purchase. Check GET /transactions/?client_reference=... or retry with the original key.

Transaction lifecycle

StatusMeaningYour action
successfulDelivered. Electricity tokens are in result.token.Fulfil the customer.
pendingSent, but the network has not confirmed. Your wallet is charged and held.Do not retry with a new key. Wait for the webhook or poll. We reconcile automatically.
failedRejected. The wallet was refunded in full, automatically, exactly once. HTTP 422 purchase_failed.Tell your customer; you may place a new order with a new key.
reversedA previously successful order reversed by BT DataPlug; refunded.Reverse the customer's order.

We only refund when the provider clearly rejected an order. A timeout or unclear answer stays pending, so you can never be refunded for something that was actually delivered.

Webhooks

Set a public HTTPS Webhook URL on your application. We POST JSON for transaction.successful, transaction.failed, transaction.pending and transaction.reversed:

{
  "id": "evt_5c1f0e...",
  "type": "transaction.successful",
  "created": 1792923304,
  "environment": "live",
  "data": { "reference": "BTD-...", "status": "successful", "...": "same object as the API" }
}

Verify the signature

Each request has X-BTDataPlug-Signature: t=<unix time>,v1=<hex>. Compute HMAC-SHA256(webhook_signing_secret, t + "." + raw_body) and compare in constant time. Reject if t is more than 5 minutes old. Your signing secret is on the application page.

Delivery and retries

  • Reply with any 2xx within 8 seconds to acknowledge. Redirects are not followed.
  • Otherwise we retry with backoff (1 min, 5 min, 30 min, 2 h, 6 h, 24 h), then stop. The console shows every attempt.
  • Delivery is at least once. Store processed id values and ignore repeats.
  • Webhooks are a convenience; GET /transactions/{reference}/ is the source of truth.

Limits and security

  • Default 60 requests/minute and 10,000/day per application (adjustable on request).
  • Store secrets in environment variables or a secrets manager. Rotate them if staff leave.
  • Use the IP whitelist when your server has a fixed IP.
  • Always verify webhook signatures; never trust an unsigned callback.
  • Do not expose this API directly to browsers or mobile apps; call it from your backend.

Verify a webhook

import hmac, hashlib, time

def verify(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    if abs(time.time() - int(parts["t"])) > 300:
        return False
    expected = hmac.new(secret.encode(), parts["t"].encode() + b"." + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, parts["v1"])
import crypto from "node:crypto";

export function verify(rawBody, header, secret) {
  const p = Object.fromEntries(header.split(",").map(s => s.split("=")));
  if (Math.abs(Date.now() / 1000 - Number(p.t)) > 300) return false;
  const expected = crypto.createHmac("sha256", secret).update(p.t + "." + rawBody).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(p.v1));
}
